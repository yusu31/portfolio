## §1 世界の構造

### §1.1 基本のリズム — 圧 → 解放 → 圧

1章は4フェーズでできている。**街の圧が解けて、また閉じる**のがこの世界の呼吸になる。

| フェーズ | 長さ | 街の建物 | 何が起こるか |
|---|---|---|---|
| **街区** | 45 | あり（壁面 x=±6.0） | 建物が左右から画面を挟む。遠景に次の施設の照明塔が見えている |
| **導入** | 10 | **なし** | 敷地の入口。フェンスの切れ目、路面の切り替わり |
| **敷地** | 28 | **なし** | コートを並走。ボールの見せ場。奥にスタンドと照明塔 |
| **退出** | 9 | **なし** | フェンスが閉じ、街の建物が戻ってくる |

1章 = **92**。4章 = **368**。

この「圧 → 解放 → 圧」は、Naughty Dog の Emilia Schatz が言う空間による感情設計そのものである
（天井を下げ壁を寄せれば緊張、開ければ解放）。屋根が無くても、
**左右から挟む建物の有無**だけで同じことができる。

### §1.2 「入った」を身体に伝える4つの装置

屋根も門も無い以上、「入った」は次の4つの同時発火で作る。**1つでも欠けると脇を掠めるだけになる。**

#### 装置1: 街の壁が消える（圧の解放）

B では建物の壁面位置は定数だった。

```
FACADE_X = ROAD_HALF(4.2) + SIDEWALK_WIDTH(1.8) = 6.0   // src/proto/b/route.ts:36
```

これを「街区フェーズにだけ建物を置く」に変える。**重要なのは実装方法**で、
B の教訓（「区間ごとに街を生成すると境界で建物が食い合う」）を踏まないため、

> **生成は全域で連続に行い、敷地フェーズに落ちた建物をフィルタで抜く。**

生成のシード連鎖を切らないので境界が食い合わない。`buildStreet()` に
除外区間の配列を渡すだけで済む。

「解放された」と読める条件は定量化できる。垂直画角 55° の半分は 27.5°、
16:9 の水平半画角は

```
atan( tan(27.5°) × 16/9 ) = atan(0.5206 × 1.7778) = 42.79°
→ 横位置 d の物体が画面端に来る前方距離 z = d / 0.9255
```

壁面 x=±6.0 の建物は、前方 6.5 ユニットで既に画面外へ抜ける。
つまり**近くの建物は常に画面外**で、圧を作っているのは**遠方の壁**である。
だから「開けた」と読ませるには、**視界深度ぶんの長さの開口が要る**。
B が `ROAD_RUNOUT = 95` を置いた根拠（「一点透視では常に70以上先が見えている」）から、

> **開口フェーズ（導入+敷地+退出）の合計 ≥ 45** を出発値とし、
> 実測で「街の壁が画面中央から消えている距離」を測って詰める。

出発値では 10 + 28 + 9 = **47**。

#### 装置2: 路面が変わる（足元で分かる）

B の `roadSurface.ts` は `STRIPS`（車道 → 縁石 → 歩道）を定数配列で持っている。
これを `t` 依存にする。

| 区間 | 車道 | 縁石 | 外側 |
|---|---|---|---|
| 街区 | アスファルト（`palette.road`） | あり（`CURB_HEIGHT = 0.16`） | 歩道（`palette.sidewalk`） |
| 敷地 | 敷地の舗装（章ごと: 土 / ハードコート / 砂） | **なし**（段差が消える = 敷地に入った合図） | コート面へ地続き |

**縁石が消えることが、路面の色より強い合図になる。** 段差は歩く体が覚えている情報だからだ。
`CURB_HEIGHT` を 0.16 → 0 へ導入フェーズの10ユニットで smootherstep する。

#### 装置3: 敷地境界（金網フェンス）

門はくぐらないが、境界は要る。**金網フェンスの切れ目**を入口にする。

- フェンスは敷地の外周に立ち、道と交わるところで途切れる
- 高さ 4.0。カメラ（路面 +2.6）より高いので、**敷地に入る直前、視界の左右をフェンスが締める**
- 既存の `netWind.ts`（風シェーダー）がそのまま使える。**風で揺れる金網**は移植資産のうち
  最もコストが低くリターンが大きい

フェンスの端部（切れ目の柱）は少し太くし、コーナーポストとして視覚的な「柱」を立てる。
**これが門の代わりになる。** 屋根が無いので「くぐる」ではなく「抜ける」。

#### 装置4: 見上げが変わる（上部構造の入れ替え）

B の `Overhead`（歩道橋・アーケード・電線）は「囲む構図」の本体で、
`maxOverheadGap()` がテストで上限を縛っている。敷地フェーズではこれを

- **照明塔**（高さ 26〜30。§1.3 のランドマークと同一の物）
- **防球ネット**（サッカー章のみ。上を横切る巨大な網）

に差し替える。街区では上が閉じ、敷地では上が抜ける（照明塔が点在するだけ）。
**上を見上げたときの情報量が入れ替わる**ことで、同じ屋外でも別の場所だと分かる。

> **4装置の同時発火**: 導入フェーズ 10 ユニットの中で、
> 縁石が消え、建物が途切れ、フェンスの柱を抜け、上部構造が照明塔へ替わる。
> **どれか1つだけを 10 ユニットかけて変えると鈍い。4つ同時に変えると「入った」になる。**

### §1.3 遠景予告 — ランドマークの配置（weenie）

Disney Imagineering の「weenie」（視覚的な磁石で人を前へ引く）を、そのまま採る。
スクロールに目的が生まれるので、Lempens の「区間ごとの動詞」に相当する役割も果たす。

**ランドマークが手前の建物に隠れないための条件を計算した。**

カメラが街区にいて、109 ユニット先の敷地を見ているとする。

```
手前 20 ユニットの建物（壁面 x=6.0）の水平角 = atan(6.0 / 20)  = 16.7°
                                上端の仰角 = atan((18-2.6)/20.9) = 36.4°  → 画面上端(27.5°)を超える
```

**つまり 20 先の建物は、画面中央から 16.7° の外側を上端まで塗りつぶしている。**
ランドマークがこれより外側にあると隠れる。

```
敷地中心 x=±29 に立てた場合の水平角 = atan(29/109) = 14.9°  → 隠れる（NG）
敷地の道寄り x=±12 に立てた場合    = atan(12/109) =  6.3°  → 隠れない（OK）
```

> **決定: ランドマーク（照明塔）は敷地の中心ではなく、道寄り（近サイドライン + 3 ≈ x=±12）に立てる。
> 高さは 26〜30。**（街の建物の最大高 18 に対し +8 以上）

高さの検算: 109 先・高さ 28 の塔の仰角は `atan(25.4/109) = 13.1°` で、画面の上半分に頭が出る。

**可視距離の目標: 110 以上手前から見えていること。** ただしフォグに負けてはならない。
B のパレットの `fogFar` は Morning 210 / Noon 220 / Amber 190 / **Night 160**。
夜が最も厳しいが 160 > 110 なので成立する。夜はむしろ**照明塔が点灯する**ので、
フォグの中の光点として最も強く見える。

| 章 | ランドマーク | 高さ |
|---|---|---|
| Projects（サッカー） | 照明塔 ×2 + 防球ネットの支柱 | 28 |
| Skills（バスケ） | 照明塔 ×2 + 大型スコアボード | 26 |
| About（バレー） | 照明塔 ×2 + 観客席スタンドの背面 | 26 |
| Contact | フィニッシュゲート（既存 `FINISH_GATE_*`） | 既存値 |

### §1.4 座標

道は -Z 方向へ進む。`t` は道に沿った距離。

```
ROAD_LEAD    = 16    （B と同じ。カメラが t=0 で後方にいるため）
ROAD_RUNOUT  = 95    （B と同じ。一点透視の奥を切らない）
TOTAL_LENGTH = 368   （4章 × 92）
```

| 章 | 街区 | 導入 | 敷地 | 退出 | 敷地中心 z |
|---|---|---|---|---|---|
| 1 Projects | 0 〜 -45 | -45 〜 -55 | -55 〜 -83 | -83 〜 -92 | **-69** |
| 2 Skills | -92 〜 -137 | -137 〜 -147 | -147 〜 -175 | -175 〜 -184 | **-161** |
| 3 About | -184 〜 -229 | -229 〜 -239 | -239 〜 -267 | -267 〜 -276 | **-253** |
| 4 Contact | -276 〜 -321 | -321 〜 -331 | プラザ -331 〜 -368 | — | **-349.5** |

**近サイドライン（道側の辺）は全章 x = ±9.0**（道の縁 6.0 + 敷地の余白 3.0）に揃える。
ヴェニュー中心はコート半幅ぶん外へ出す。左右は ② の慣習を引き継いで交互にする
（相対オフセットの符号を書き換えずに済むため）。

```
projects: (-29.25, 0, -69)     近サイドライン x = -29.25 + 20.25 = -9.0 ✓
skills  : ( 28.95, 0, -161)    近サイドライン x =  28.95 - 19.95 =  9.0 ✓
about   : (-28.95, 0, -253)    近サイドライン x = -28.95 + 19.95 = -9.0 ✓
contact : (  0,    0, -349.5)  道の正面（終着プラザ）
```

参考: ② では近サイドラインが x=0 だった（「カメラは引かないのでコートを3倍化し、
タッチライン際すれすれを並走させる」設計）。**今回はカメラが引ける**（§3）ので
その根拠は消え、球は道の上を離れない（§2.2）ので **9.0 外へ出す**。
これが HANDOFF の未解決事項「Q6c と Q8a の両立」に対する答えになる。

### §1.5 道の形

B の `elevationAt` / `lateralAt` をそのまま採る（下り坂 + 緩いうねり + 緩いカーブ）。
全長が 280 → 368 に伸びるので、周期パラメータだけ引き直す。

```
OVERALL_DROP     = 26 → 34   （u あたりの勾配を B と同じに保つ: 26 × 368/280 = 34.2）
UNDULATION       = 3.4       （振幅は据え置き。周期は u 基準なので自動で伸びる）
CURVE_AMPLITUDE  = 5.0       （据え置き。上げると消失点が画面中央から外れる = テストで縛る）
```

**下り坂であることには §7 で追加の役目がある**（落下の受け皿）。

## §2 章の割り当て

### §2.1 二層構造 — 街区が物語、敷地がセクション

B の `LEGS` は物語ラベル（体育館へ続く道 / 校庭沿い / 街の坂 / オフィス街）を持っていた。
② の `SECTION_RANGES` はポートフォリオのセクション（projects / skills / about / contact）を持っていた。
**この2つは競合しない。層が違う。**

> **街区フェーズ = 物語（体育教師 → エンジニア）。敷地フェーズ = セクション（Projects / Skills / About / Contact）。**

街を歩きながら来歴を語り、施設に着いたら作品を見せる。街の性格（建物の高さ・密度・パレット）が
章ごとに変わっていくことが、そのまま時間の経過になる。

| 章 | 街区の物語 | 敷地 = セクション | 動詞 | パレット | 建物高さ |
|---|---|---|---|---|---|
| 1 | 教えていた場所 | **Projects** / 屋外サッカーグラウンド | **蹴り込む** | Morning | [7, 12] |
| 2 | 走らせて、走っていた | **Skills** / 屋外バスケコート | **撃ち上げる** | Noon | [7, 14] |
| 3 | 独学の時間 | **About** / 屋外バレーコート | **受けて、上げる** | Amber | [9, 17] |
| 4 | いま作っている場所 | **Contact** / 終着プラザ | **着地する** | Night | [10, 18] |

パレットは B の4つ（Morning / Noon / Amber / Night）をそのまま採る。朝→夜へ空間的に移り変わる。

**未解決の既知バグ**: B の Amber 区間はオーバーレイ文字が読めない（橙の差し色を橙の空に重ねている）。
実装時に UI 文字色を `paletteAt(t)` から導出し、ΔE 閾値（§5.4）で縛る。

### §2.2 球は道を離れない — 施設は「的」であって「通り道」ではない

**これが今回の設計の要になる判断。**

「1本道を連続前進する」が必須要件である以上、球が道を外れてコートの中へ入ることはできない。
では見せ場はどこで起きるのか。

> **球は道の上を進み続ける。見せ場は「道の上から施設へ向けて」起こる。**

- Projects: 道を走りながらドリブル → **道の上からゴールへ蹴り込む** → ネットが揺れ、跳ね返って道へ戻る
- Skills: 戻ってきた球を道の上でキャッチ → **道からリングへ撃ち上げる** → リングを抜けて道へ落ちる
- About: 落ちてきた球を道の上でレシーブ → トス → **ネット越しにスパイク**
- Contact: 終着プラザへ着地して静止

この構造には3つの利点がある。

1. **1本道が守られる**（骨格の必須要件）
2. **既存の弾道ソルバー（`ball/physics/ballistic-trajectory.ts`）がそのまま生きる。** 距離が変わるだけ
3. **ネット物理（ベイク Verlet）が主役になる。** ② では通過するだけだったネットが、
   「撃ち込む的」になることで揺れが見せ場そのものになる

**一般則: 「見せ場の的」は敷地の道寄り3分の1に置く。コートの奥は絵（スタンド・照明塔）として使う。**

理由は §1.3 と同じ幾何にある。水平方向は画面幅で厳しく制限されるが（`d = 0.9255z`）、
**高さ方向は仰角で決まるので緩い**。

```
遠サイドライン x=48.9 の白線: 画面に入るには前方 53 必要 → 並走中は見えない
同じ位置の高さ 12 のスタンド : 前方 20 での仰角 atan(12/52.8) = 12.8° → 画面に入る
```

> **水平には画面外でも、垂直には入る。** だからコートの遠い辺は白線として見せず、
> **高さのある構造物（スタンド・フェンス・照明塔）で「場の終わり」を示す。**

### §2.3 的の位置（再導出が必要な箇所）

② の構造物オフセットは「近サイドラインが x=0」を前提にしていたので、そのままでは
的が道から遠すぎる。**的を道寄りへ寄せ直す**のが再導出の中身になる。

| 的 | ② の道からの水平距離 | 新しい目標 | 書き換える定数 |
|---|---|---|---|
| サッカーゴール前面 | 実質 6.5 | **12 前後** | `SOCCER_GOAL_GROUP_OFFSET.x` |
| バスケリング | 実質 5.1 | **11 前後** | `HOOP_GROUP_OFFSET.x` |
| バレーネット | 実質 0 | **10 前後** | `VOLLEY_NET_GROUP_OFFSET.x` |

「12 前後」の根拠: 水平距離 12 の的は、前方 13 ユニットで画面端に来る（`12/0.9255 = 13.0`）。
つまり**的が画面に入っているのは前方 13 以上の間**。敷地の長さ 28 に対して十分な滞在時間がある。

**`RING_OFFSET` は触らない**（HANDOFF の禁止事項）。動かすのは `HOOP_GROUP_OFFSET` の側。

## §3 カメラの文法

### §3.1 画角と、2つのカメラ姿勢

```
fov = 55   （B。「強い一点透視」の実体。A の 28 とは真逆）
```

B は主役が人（身長 1.8）、② は主役が球（半径 1.5）だったので、追従の4値が全く違う。

| | B（人物） | ②（球体） |
|---|---|---|
| dBack | 6.5 | 4.5 |
| dUp | 2.6 | 3.0 |
| lookAhead | **14** | **2** |
| lookUp | 2.2 | 1.5 |

**`lookAhead` の差が「一点透視の強さ」の正体である。** B が遠くを見ているから道が奥へ消える。
② は足元寄りなので、球は大きく写るが街の奥行きが出ない。

これは「見た目は B / 骨格は Lempens」の衝突点そのものなので、**計算で確かめた。**

### §3.2 検算 — B のカメラ値は球にそのまま使える

球（半径 1.5、中心は路面 +1.5）を B の値で撮ったときの画面内位置を求める。

```
カメラ位置 = anchor − heading×6.5 + (0, 2.6, 0)
視線ターゲット = anchor + heading×14 + (0, 2.2, 0)

球へのベクトル v = (0, 1.5−2.6, 6.5) = (0, −1.1, 6.5)
視線方向 f = normalize(0, 2.2−2.6, 6.5+14) = (0, −0.01951, 0.99981)

depth   = v・f = 6.520
up 成分 = −0.9730
screenY = −0.9730 / 6.520 / tan(27.5°) = −0.287       … 画面中央やや下 ✓
画面上の半径 = 1.5 / (6.520 × 0.5206) = 0.442
  → 上端 +0.155 / 下端 −0.729                          … 全身がフレーム内 ✓
見かけの大きさ = 画面高の 44%
```

**B のカメラ値をそのまま球に使うと、球は「画面中央やや下・全身がフレーム内・画面高の 44%」で写る。**
参考例①の「主役は画面中央やや下、身長は画面高の約 1/4」という観察と同じ構図に乗る
（球は人より大きく写るが、主役が球だけなので存在感としてはこれで正しい）。

同じ計算を ② の値でやると `screenY = −0.726` / 見かけ 57% で、
**下側が 3 割ほど画面外に切れる**（②のドキュメントが記録している「クロップ率平均 29%」と一致する）。

### §3.3 決定 — 街区は B 値、見せ場は ② 値

> **街区フェーズ = B 値（一点透視を強く、街を見せる）**
> **見せ場 = ② 値（球に寄る、ボールを追う）**

| 区間 | dBack | dUp | lookAhead | lookUp | 見かけの大きさ |
|---|---|---|---|---|---|
| 街区・導入・退出 | 6.5 | 2.6 | 14 | 2.2 | 44% |
| 敷地（見せ場） | 4.5 | 3.0 | 2 | 1.5 | 57% |
| 弾道の飛行中（arc） | 7 | 4.5 | 2 | 1.5 | — |
| 撃ち上げ（引き） | **17** | 3.8 | 2 | 1.5 | — |
| 落下（dive） | 1.5 | 7 | 0 | 0 | — |

**引きの機構は既に ② にある。** `freeThrowBlendT` が `D_BACK` を 4.5 → 17 へ smootherstep で
渡している（`src/journey/camera.ts:96`）。バックボードが「白い壁」になった問題を
**カメラを引くことで**解いた実績があり、同じ機構で「街区 ↔ 見せ場」も作れる。

### §3.4 機構の一般化 — blendT をテーブルにする

現在の `getCameraOffset(u)` は `arcBlendT` / `freeThrowBlendT` / `diveBlendT` の3つを
ハードコードで連鎖 lerp している。章が増えるたびに関数が増えるので、テーブルへ移す。

```ts
type CameraBeat = {
  from: number          // u
  to: number
  ease: number          // 台形の立ち上がり幅（0.5 で三角形 = 現行の diveBlendT 相当）
  peakAt?: number       // 省略時は (from+to)/2
  offset: Partial<CameraOffset>
}
```

- 現行の `diveBlendT`（三角形）= `ease: 0.5`
- 現行の `arcBlendT`（台形・前後 12%）= `ease: 0.12`
- **区間が重ならないことをテストで縛る**（現行コードのコメントが前提にしている性質を、
  暗黙の了解からテストへ格上げする）

`applyCameraAttitude`（roll / pitch のキーフレーム）は**無変更で後段に残す**。既存契約のまま。

### §3.5 fov のパンチ（速度感）

fov は基本 55 固定だが、**落下とスパイクの瞬間だけ 55 → 68 へ吹かせて戻す**。
FOV を上げると画面端の物体が速く流れるため、速度の錯覚が最も安く手に入る手法である
（[Adding the Feeling of Speed](https://elliotdev.gg/adding-the-feeling-of-speed/)）。

- 立ち上がり 0.35 秒相当 / 戻り 0.8 秒相当を smootherstep
- **一点透視の強さが変わる**ので、見せ場の一瞬だけに限る。街区では絶対に触らない
- `prefers-reduced-motion` では振れ幅を 0 にする（既存 `useReducedMotion` に乗せる）

## §4 章の切替 — 二重実装をどう分けるか

「章内はグラデーション（B式）+ 章間はワープ（Lempens式）」をどう共存させるか。
**2つの実装が互いに直交するように軸を分ける。**

> **色は `t` の関数（1実装）。ワープは `offset → t` の写像（1実装）。**

### §4.1 色 — 位置ごとに焼く（B式・そのまま移植）

B の `paletteAt(t)` をそのまま採る。物の色はその物自身の位置で引く。

```
PALETTE_BLEND = 0.24   // 区間の終盤 24% だけ次のパレットへ渡す
```

**この 0.24 には根拠がある**（B の設計判断3）: 区間全部を使って渡すと、
中央が常に2色の 50/50 混色になり「パレットを絞る」が成立しなくなる。

色は `t` の連続関数なので、**ワープしても色は飛ばない**（`t` 自体は連続だから）。
急に変わるが、その瞬間はワープ VFX が画面を覆っている。

### §4.2 ワープ — スクロールと距離の写像に段差を入れる

```ts
distanceAt(offset): number
```

② では弧長ベースの線形写像だった。ここを**区分的に非線形**にする。

| 区間 | 1ページあたりの前進量 | 意図 |
|---|---|---|
| 通常 | 10.4（②/B と同じ） | 街を歩く速度 |
| **ワープ** | **42**（4倍速） | 25 ユニットを 0.6 ページで飛ぶ |
| **見せ場** | **6.5** | ボールの弾道を読ませるため減速 |

**ワープを撃つ位置**: 敷地を出て、**街が閉じきった後の街区**。

| ワープ | z 区間 | 長さ |
|---|---|---|
| 1（Projects → Skills） | -97 〜 -122 | 25 |
| 2（Skills → About） | -189 〜 -214 | 25 |
| 3（About → Contact） | -281 〜 -306 | 25 |

**開けた場所でワープしない理由**: 開けた場所は参照物が無いので「飛んだ」ことが分からない。
閉じた街区なら、前後で街の建物が入れ替わっても違和感が出ない。Lempens が
「章の切替をワープで隠す」と言うときの「隠す」はこの意味である。

移植する資産: `WarpFlash.tsx` / `warpVfxEnvelope.ts`（世界の形に依存しない）。

### §4.3 スクロール総量

```
実スクロール距離 = 368 − (3 × 25) = 293
PAGES = 293/10.4 + 3×0.6 ≈ 30
```

② は `PAGES = 27`、B も同水準。**世界は 368 に伸びたのに、スクロール量はほぼ変わらない。**
これがワープを入れる実利でもある。

## §7 落下演出の代替案 — 球体は回転で落下感を出せない

### §7.1 問題の再確認

Lempens のスカイダイブの本体は「**カメラを回さず、アバター本人を宙返りさせる** + シェイク + パーティクル」
（`github.com/sebastien-lempens/webgl-skydiving` で確認済み）。
主役を球体のみに決めたので、**球には向きが無く、宙返りが成立しない。**

### §7.2 6層で作る

回転の代わりに、**6つの手がかりを同時に重ねる**。単独ではどれも弱い。

#### 層1: 世界が上へ流れる ★ 最重要

球は無地なので、**球自身は速度の手がかりを一切持たない**。速度は
「脇を通過する物体がどれだけ速く流れるか」だけで読まれる。
だから**落下の脇に垂直な参照物が要る**。

> **落下は街区の上で起こす。開けた敷地の上では絶対に起こさない。**
> 敷地は参照物が無いので、どれだけ速く落ちても「浮いている」ように見える。

`§4.2` でワープを街区に置いたのと同じ理由であり、**落下 → ワープの順に並べれば
落下の終わりをワープで隠せる**（Lempens と同じ手順）。

参照物: 街の建物の壁（窓のグリッドがあるので流れが読める — §5.4 の窓が効く）、電柱、照明塔。
**落下経路のすぐ脇（水平距離 6〜10）に垂直材を通す。**

#### 層2: 進行方向への引き伸ばし（stretch）★ 球ならではの解

> **球に「向き」は無いが、「軸」は与えられる。速度ベクトルが軸になる。**

アニメーションの古典 squash & stretch を、回転の代替として使う。

```
速度方向へ  scale = 1.00 → 1.35
直交方向へ  scale = 1.00 → 0.88     （0.88² × 1.35 = 1.045 ≒ 体積保存）
着地の瞬間  進行方向 0.75 / 直交 1.15 でスカッシュ → 2〜3 バウンドで 1.0 へ
```

クリスタル球は透過と屈折を持つので、**引き伸ばすと屈折像も歪む**。
これは望ましい副作用で、「速いから歪んでいる」に読める。

実装は `CrystalBall.tsx` の**外側でグループの `scale` と `quaternion` を操作する**だけ
（球体本体のレシピには触らない — メモリの決定を守る）。
`quaternion` は速度ベクトルを局所 +Z に合わせる回転。**見た目は回っていないが、軸は向いている。**

#### 層3: 軌跡（トレイル）

球の後ろにリボンを引く。手法は `TrailRendererJS` 方式（局所空間の頭点列を
ワールド変換して既存の頭に繋ぎ、ジオメトリを伸ばす）を自前実装する
（[TrailRendererJS](https://github.com/mkkellogg/TrailRendererJS)）。

- 色は球の発光色（オレンジ）から `palette.accent` へ、末端で `sky` へ抜ける
- **長さを速度に比例させる。** 一定長だと「常に速い」ことになって速度差が読めなくなる
- 加算ブレンド + `depthWrite: false`

#### 層4: fov のパンチ

§3.5。55 → 68。**最も安く効く**（画面端の流れが直接速くなる）。

#### 層5: カメラシェイク

`applyCameraAttitude` の後段に足す。**振幅は必ず小さく。**

```
周波数 ≈ 18 Hz（Perlin ノイズで非周期に）
振幅   ≈ 0.02 rad（roll / pitch のみ。yaw は入れない = 進行方向がブレると酔う）
```

やりすぎると不快になる（「a little goes a long way」）ので、
**§7.2 の層1〜4 で足りない分だけを足す**という順序で調整する。
`prefers-reduced-motion` では 0。

#### 層6: 雲ヴェールと、地面の影

- `DiveCloudVeil`（既存資産）を落下の入口と出口に被せる。ワープと役割が近いので**同時に撃たない**
- **真下の影が近づいてくる**。高度の唯一の直接的な手がかりになる。
  落下経路の直下に地面があることを確認する（② には `groundHole` があり、
  Issue #344「地面の穴が通常再生では見えない」が未解決。新ルートでは穴を開けない前提で設計する）

### §7.3 どこで落ちるか

Skills（バスケ）でリングを抜けた球が、**次の街区の下り坂を落ちていく**。

B の道は `OVERALL_DROP` で下っている。**落下を道の勾配と結びつける**ことで、
「落ちた先にちゃんと道が続いている」が絵として成立する。

```
リングを抜ける（z ≈ -161 付近） → 街が閉じる（z = -184） → 落下（-184 〜 -189）
→ ワープ（-189 〜 -214） → About の街区へ
```

## §8 リッチにする工夫

> ユーザー指示: 「チープにならなければの話。しっかりリッチにできるよう工夫し、都度リサーチして」

投資先は**背景とオブジェクト**であり、クリスタル球ではない（球は現状で完成している）。

### §8.1 壁の情報量 — 窓と看板（最優先）

B の既知の弱点は「**建物が無地の板**。窓・看板が無く近景の壁が大きな単色面になる」だった。
C が既に解いているので移植する（§5.4）。

- **窓の点灯パターンを建物ごとに決定的乱数で焼く。** 毎フレーム更新しない
  （B の設計判断2「位置ごとに焼けば毎フレームのインスタンス色更新は不要で、絵としてもそちらが正しい」）
- 夜のパレットでは窓が唯一の明るい要素になる。`MIN_WINDOW_STRUCTURE_DELTA_E = 20` で縛る
- 日本の街なので**縦看板**を混ぜる。`palette.accent` のみ使用（パレット絞り込みを崩さない）

### §8.2 揺れる金網（既存資産の最大活用）

`netWind.ts` の風シェーダーを**敷地のフェンスと防球ネット**へ流用する。
ゴールネットのために書いた資産が、そのまま「街区にはない、敷地だけの質感」になる。

**巨大な網が上を横切る**（サッカー章の防球ネット）のは、
既存の Overhead（歩道橋・電線）より情報量が多く、しかも動く。

### §8.3 照明塔（ランドマーク兼、夜の光源）

- 昼: シルエットとして遠景予告（§1.3）
- 夜: **点灯する。** フォグの中の光点として最も遠くまで届く
- ゴッドレイは重いので使わない。代わりに**円錐メッシュに加算ブレンド + フレネル減衰**を焼く

### §8.4 遠景のスカイライン

施設の向こう（x が大きい側）に、低ポリのビル群をビルボードで置く。
**「街の中にある施設」であることが、施設の向こうにも街があることで初めて伝わる。**
`fogFar` に溶ける位置に置くので、ポリゴン予算はほぼ食わない。

### §8.5 夜の濡れた路面

スクリーンスペース反射は重い。代わりに**路面に空色の薄い鏡面ストライプを焼く**
（進行方向に伸びる細長い明度パッチ）。Night パレットでのみ有効にする。

### §8.6 雲

`drei` の `<Clouds>`。**`frustumCulled={false}` が必須**
（ワールド原点から離れた `<Cloud>` は既定 true では描画されない — 既知の罠）。

### §8.7 スクロールの緩急（§4.2 の再掲）

見せ場で減速し、ワープで加速する。**一定速度のスクロールは、それだけでチープに見える。**

## §9 輪郭線 — 決め方だけを決める（採否は保留）

B の `?ol=0` 撮り比べでは差が限定的だった。**「輪郭線が要る理由は壁に情報が無いから溶ける」
とも言えるので、窓を入れると要否が変わる。**

> **窓・看板（§8.1）を入れた後に測って決める。実装順序は §10 のとおり。**

### 測る量

「輪郭線が無いと溶ける」という主観語を、測れる量に翻訳する。

| 測る対象 | 量 | 判定 |
|---|---|---|
| 画面上で前後に重なる建物ペア | 両者の `deltaE` | ≥ `MIN_STRUCTURE_DELTA_E`(10) なら線なしでも分離する |
| 同ペアの境界コントラスト | 境界の左右 3px の平均輝度差 | 実測して閾値を決める |
| 建物と空の境界（屋根） | `deltaE` | ≥ `MIN_ROOF_SKY_DELTA_E`(20) |

### 判定手順

1. 窓・看板を入れる
2. 全4章 × 代表点3箇所を `?ol=0` / `?ol=1` で撮る（計 24 枚）
3. 各枚で上の3量を測る
4. **`?ol=0` で全閾値を満たすなら輪郭線は不要。** 満たさない章がある場合、
   その章だけ有効にするのではなく**全章で有効にする**（B の教訓「線は構図に従属する」より、
   構図が同じなら扱いも同じであるべき）

### 記録する値

**壊れていた側の実測値も必ず書き残す。**
C が `MIN_STRUCTURE_DELTA_E = 10` に対して「旧 Night 7.0 / 旧 Misty 7.8 が塊に溶ける側」と
記録していたから、後から閾値の妥当性を判断できた。同じ形式で残す。

## §11 テストで縛るもの

A / B / ② で確立した「**仕様を目分量ではなく数値で固定する**」を継承する。
作り込みが粗い段階でも方向の定義だけは崩れないようにするため。

### 移植する縛り

| テスト | 縛る対象 | 出典 |
|---|---|---|
| `vanishingOffsetDeg(t) < 上限` | 一点透視の強さ（消失点が画面中央から外れない） | B |
| `enclosureElevationDeg(h) > 27.5°` | **街区で**建物が画面上端より上まで伸びる（囲む構図） | B |
| `maxOverheadGap() < 上限` | 上部構造の隙間（空に抜けると囲む構図が壊れる） | B |
| ΔE 7閾値 | 色が溶けない | C |
| 視線 AABB / 構造物クリアランス | カメラが構造物にめり込まない | ② |
| `totalLegLength() === TOTAL_LENGTH` | 章の合計と経路長の一致 | B |
| 街の生成が境界で食い合わない | 建物の重なり検出 | B |

### 新しく足す縛り

| テスト | 縛る対象 | なぜ要るか |
|---|---|---|
| **`enclosureElevationDeg(h, facade) < 27.5°` が敷地で成立** | **敷地で開けている** | 「開ける型」の仕様そのもの。これが無いと開口が骨抜きになっても気づけない |
| **ランドマークの可視距離 ≥ 110、かつ手前の建物に隠れない** | 遠景予告 | §1.3 の角度計算をテストで固定する |
| **カメラの blendT 区間が重ならない** | §3.4 のテーブル化 | 現行コードがコメントで前提にしている性質を、テストへ格上げする |
| **球の `screenY` と見かけ大きさが目標範囲内** | §3.2 の構図 | 街区 44% / 見せ場 57% |
| **落下区間の脇に垂直参照物が存在する** | §7 層1 | 「参照物が無いと速度が読めない」を仕様として固定する |

### QA ノブ（最初から入れる）

A / B / C で確立した運用をそのまま採る。**検証したい違いはクエリで切り替えられるようにする。**

```
?leg=N        章を直接指定（スクロールを見なくなるのでカメラが静止し、2回目のポーリングで収束）
?at=0〜1      章の中の位置
?ph=street|open|venue|exit   フェーズ直接指定
?ol=0         輪郭線オフ（§9 の判定に必須）
?fall=0       落下演出の各層を個別にオフ（?fall=trail,stretch,fov,shake で層を選択）
?warp=0       ワープ無効（経路を連続で確認する）
?land=0       ランドマーク非表示
```

スクリーンショットは既存の `scripts/qa-proto-shots.mjs <route> <outDir> <plansJson>`。
**Git Bash からは `MSYS_NO_PATHCONV=1` が必須。ヘッデッド必須。**
チェックポイントごとに単一 wheel + 安定するまでポーリング（この開発機で唯一収束する手順）。

## §12 却下した案とその理由

| 却下した案 | 理由 |
|---|---|
| **通り抜け型（両端の開いた大屋根）** | 私の推奨案だったが、ユーザーが「開ける型」を選択。屋根で空が切れると B の最大の武器（夕景1トーンを位置ごとに焼く）を捨てることになる、という批評家視点の指摘が採られた |
| **屋内型（建物の中で章が完結）** | 一点透視の消失点が壁で止まる。`ROAD_RUNOUT = 95` の前提（常に70以上先が見えている）が章のたびに崩れる。「1本道を連続前進」と構造的に矛盾する |
| **街が変形して立ち上がる** | B の設計判断2「パレットを位置ごとに焼く（世界は静的）」と衝突する。毎フレーム更新が復活し、B が捨てた設計へ逆戻りする |
| **章ごとに入り方を変える** | 各章に固有実装が要り工数が4倍化する。「1本道の旅」としてのリズムも崩れる |
| **球がコートの中へ入る** | 「1本道を連続前進」が守れない。施設を「的」にすることで、1本道・弾道ソルバー・ネット物理の3つが同時に生きる（§2.2） |
| **人物アバターを入れる** | 主役は球体のみと確定済み。ただし「球が主役として成立するのは C だけ」という SESSION7 の理由は誤りで、② が反証になっている |
| **C の空中歩廊** | C の俯瞰構図専用。B の一点透視では上部構造は歩道橋・電線で足りる |
| **C の走路の蛇行** | C の固定カメラ専用。連続追走では蛇行が消失点を振り、一点透視を壊す |
| **`journey/DepthOutline.tsx` の流用** | 現行シーン固有の制約（drei Cloud が depth を書かない）への対処。B が既に却下している |
| **回転で落下感を出す** | 球体に向きが無いので成立しない。代わりに**速度ベクトルを軸にした stretch**（§7.2 層2）で置き換える |
